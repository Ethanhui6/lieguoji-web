# WEB-04-37：战乱看海时的整图重绘减负

- 日期：2026-10-11；源码提交 `c6cc736`，分支 `codex/ph06-world-generation`
- 仅本机试玩：`http://127.0.0.1:5315/?fms=1`；旧端口与存档未迁移、清理或覆盖
- 限定范围：战斗接触**装饰光效**在军队已经静止于已确认画面时，最多每 250ms 触发一次整图重绘。实际部队移动仍按 RAF 更新；开战、战斗、推进、日期、战史、存档均不读这个装饰节奏。

## 为什么改这里

同一 `1337` 地形种子、六国、60 城、战乱开局、4× 持续十秒的本机桌面 Chromium 观察：修复前两次独立运行，在十秒内分别收到 3 和 4 个 480-tick 已确认批次；同时 `PerformanceObserver` 几乎连续记录约 100ms 的主线程长任务。独立 Node 内核采样在一个固定网格六国战乱夹具上，20 日五批 `executeDisplay` 合计约 1.266s（约 15.8 日/秒），提示浏览器绘制/交付还有明显成本；**Node 夹具并非浏览器地形，不直接相除作性能结论**。浏览器 CPU profile 的大量样本记为 program/idle，不能单凭它归因某个 JS 函数。

源码审查发现只要有当前战斗接触，原 RAF 条件就会不停调用 `drawCombatMarkers47` + `renderer.refresh()`；后者重绘整个地形、政区、河流、文字、部队，而不仅是光效。新条件仅在光效到期时做这次装饰刷新；位置仍在已确认军队行进时逐帧更新，战场状态变化仍在 Worker ACK 的完整 `paint` 中更新。

相同创建流程的新浏览器运行十秒收到 **8 个** 480-tick 批次（第 32 日的 tick 3840 于约 9.441 秒确认），期间长任务多数约 57–70ms，ACK 首帧约 107–123ms。此前两次同流程到约第 12／16 日；这是这台电脑、桌面 Chromium、一次候选构建的**观察结果**，不是原作速度、真机帧率、稳定基准或保证倍速。长任务仍非常频繁，移动期间整图渲染仍昂贵；下一项应把静态地形/文字与动态军队、战斗光效拆开或缓存，再量化实际帧时间。

回归：`npm run typecheck`、`npm run lint`、`npm run build`（85 个允许产物）通过；桌面 Chromium 的玩家实际调遣、连续位置、暂停地图拾取 1/1；桌面与手机尺寸 Chromium 的正常六国战乱世界、陆海行动、详情打开继续推进、保存刷新恢复各 1/1。手机尺寸截图还显示**初始大陆过小、大片纯蓝海面，打开战役详情后地图被面板遮挡**；功能回归通过不能掩盖这个未通过的视觉体验。手机尺寸仿真不是 iPhone 13 Pro Max Safari/Chrome 真机。原作视觉与战争节奏仍未验收；光效的 250ms 更新是当前性能取舍，不当作最终动画设计。

`game-cpu.cpuprofile` 与 `browser-main-cpu.cpuprofile` 是本地网页代码的原始性能样本；不含原作安装包、账号资料、存档或令牌。没有 push、Pages、Cloudflare 或正式站变更。
